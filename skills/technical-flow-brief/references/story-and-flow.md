# 总览、阶段流程与局部展开

## 一套连续的讲解，而不是彼此独立的图

总览回答：“请求从哪里来，经过哪些责任层，资源和数据交给谁，最后由什么确认完成？”细节页沿总览中的同一个节点继续解释，不换一套命名，也不把原节点重新写成泛泛总结。

默认组织：

1. 总览：主要入口、跨层交接、执行主体和完成依赖。
2. 入口与选择：参数整理、配置读取、拓扑、算法/后端选择。
3. 资源准备：查询/复用、内存、执行队列、端点和通道。
4. 建链与交换：创建对象、推进连接、交换描述、回填可用句柄。
5. 发射与执行：Host 提交、设备入口、算法展开、真实数据路径。
6. 同步与完成：输入就绪、阶段等待、主从汇合、用户流继续。
7. 测试清单：共用能力、路径差异、条件和观测点。

这是覆盖问题的检查顺序，不是固定七页。实际缺少某阶段就省去；一个复杂阶段可多页展开。用户只要改表时，不重做已认可的流程图。

## 首选流程版式：阶段 × 责任层

横轴放逻辑阶段，纵轴放真实责任主体，如上层调用者、框架 Host、通信控制面、运行时、设备算法、通信数据面。按任务调整，不把具体系统的层名硬套到别的主题。

- 顶部紧凑阶段条给全局方向，左侧责任标签帮助定位所有权。
- 同一行从左向右推进；下调用跨层向下，返回或通知跨层指向明确接收者。
- 后一阶段无需沿长折线绕回页首；必要的返回边走局部预留通道。
- 只连真正存在的交接。阶段间的依赖不是每对 API 都直接调用，图例须说明。
- 空白格表示该主体在此阶段无动作，不填“处理”“完成”等占位框。
- 将长公共主线拆成同名阶段展开，不画蛇形串珠、满屏交叉线或几十个强制顺序编号。

**箭头区分：** 调用指向被调用函数；数据边从源 Buffer 指向目的 Buffer；通知边从发布者指向等待者；阶段依赖边说明准备条件。不要只凭颜色区别，必要时标“调用 / 数据 / 通知 / 依赖”。

## 节点需要包含什么

```text
精确函数名（必要时注明“内部方法”）
中文动作：动词 + 对象 / 产物
发生条件：仅当资源缺失 / 版本支持 / 分支选中
```

主图节点通常只放前两行，条件贴近相关分支；更多参数进备注。不能把多个不同 API 合成一个“建链”框后不再展开。总览允许概括；细节必须拆开有必要测试的接口边界。

## 建链页的四类信息

| 要讲的内容 | 图中对象 | 不要混同 |
|---|---|---|
| 申请/获取 | 资源请求、句柄、可复用对象 | 必然新建连接 |
| 创建与监听 | Endpoint、Channel、执行资源 | 用户张量传输 |
| 交换资源描述 | 地址/长度、访问描述、Notify、连接参数 | 本次输入输出数据 |
| 参数核对 | 算子类型、数量、数据类型等 | 建链全部已完成或数据已正确 |

后续的数据搬运页再画输入、中转区、远端窗口、输出。协议状态机的轮询可能调用内部方法，不要为了展示导出 API 而改写真实调用链。

## 分支、复用与异步

- 在资源层分别画查询命中、缺失创建、返回句柄；不要把“缓存”当成一个覆盖全部资源的黑盒。
- 版本兼容用二选一分支，不能要求新旧 API 同时出现；异常失败也不意味着自动切换兼容 API。
- Kernel 注册/生成指令与运行期发射分开；不要将注册期的 C++ 表达误认为每个数据块都触发的 Host API。
- 同步图标明视角。Wait 是等待事件，不是向远端发请求；异步返回不是后继用户数据立即可读。
- 错误清理仅释放本轮新建资源时，应标明对象范围，不泛化成“销毁全部资源”。

## 备注结构

备注面向讲解者，按需写：本页主线；精确符号及含义；输入和产物；分支/简化；文件、行号、版本；静态或实测证据。关键条件不只放备注，工具日志和制作过程不放备注。
